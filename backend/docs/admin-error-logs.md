# Admin issue history

The admin **Logs** page (`?section=logs`) reads `/api/admin/logs` behind the existing admin session. On main and dev it has no sidebar or profile-menu entry and is omitted from default search suggestions. On dev it is also excluded from Recently opened and Recent searches, including older browser history entries. Type the exact word `logs` in the header search (case-insensitive, surrounding spaces ignored) and select the result. Partial matches such as `log`, other queries and reopening search do not reveal the entry. This is a discovery rule; the existing admin session is the access boundary.

Today, Yesterday, 7 Days and custom dates use London calendar days, including clock changes. The API uses an exclusive end boundary, validates dates, issue kind and pagination, returns newest events first and disables response caching. Issue-type filters cover `server_error`, `access`, `slow_request`, `request_issue` and `all`.

Capture begins when the updated backend runs. It records `log.error` events and API responses with a 5xx status that have not already logged an error in their request context. Selected access/performance events are added directly to history without mislabelling them as console ERROR entries:

- Failed admin/driver sign-ins (401), missing sign-in details (400), protected requests needing sign-in (401), invalid/expired existing sessions (401), denied permissions (403), rate limiting (429) and setup/reset links rejected with the fixed `INVALID_SETUP_LINK` / `INVALID_RESET_LINK` response codes.
- Request timeouts (408/504), missing items/routes (404), conflicts (409), oversized requests (413) and connections closed before the response finishes. Connection interruption is not treated as proof of a server error or successful response; the default unsent status is omitted.
- Completed successful API requests taking at least **10 seconds**. Set `ADMIN_LOG_SLOW_REQUEST_MS` before startup to change this (1,000–300,000 ms; invalid values fall back to 10,000). Elapsed time uses the monotonic clock from middleware entry until response completion, including request-body receipt; it is not browser load time or a pure CPU-time measurement. Slow success entries retain the actual success status and explicitly state that the request did not fail. Slow failed requests use their failure category instead of a duplicate slow event.

Routine successful traffic, ordinary form validation, normal signed-out `/me` checks without the relevant session cookie, expected event-stream durations/closures, general debug/info/warn messages, host/OS logs and earlier console output remain excluded. Invalid session wording does not assume the cookie was definitely expired: expiry, invalidation and invalid cookies share a response. No entered password, account email, session value, IP address or reset token is captured. Only a fixed response-code allowlist is inspected; response bodies are passed through unchanged and are not copied.

Recovery is not inferred: a past event is not evidence of a current outage. The original technical error console logs remain available to developers, linked by request ID when present. Selected access/performance events also emit a structured console INFO entry (subject to the configured log level) with the same request ID and diagnostic metadata.

New entries in `admin_server_errors` include HTTP method, sanitized endpoint/route template, operation, initiating page when known, request start, response/error timing, build ID and a UUID identifying the server run. Dynamic emails, tokens and other path values become placeholders. Only fixed page labels are extracted from the Referer; the URL itself is discarded. A page identifies the originating browser view, not proof that a background operation belongs exclusively to that tab. Missing Referer means no guessed page. `X-Request-ID` is returned on API responses for correlation in browser Network tools.

Selected query filters (`from`, `to`, `page`, `pageSize`, `limit`, `detail`, `groupBy`) are retained only after date, number and enum validation. Searches, request bodies, headers, passwords, raw query strings and other query values are excluded. Request-context errors receive this metadata even when their existing `log.error` prevents a duplicate 5xx entry. Error snapshots show elapsed time at the error; completion/connection-close entries show the complete observed duration. Completed durations are frozen so later background work cannot inflate them.

Mongo command monitoring records only allowlisted collection/command names and elapsed time. It does not retain commands, filters, result documents, errors or connection addresses. Concurrent commands stay associated with their initiating request; totals aggregate by operation, with count, longest call, failures and pending count. Parallel totals can exceed wall time. These are command/network timings after connection checkout, not pool-wait time or all server CPU time. Collection names outside the allowlist become `other`. At most 20 timing groups are collected and the 12 slowest are returned; the command correlation map is bounded. Logging's own database operations are excluded and no new database reads are introduced by diagnostics.

The Compose release passes the deployed `VITE_BUILD_ID` to the backend as `APP_BUILD_ID`; local runs default to `local`. “Request details” and “Copy reference” include the diagnostic fields so investigation does not depend on a replaced container's console history. Older records remain readable and explicitly show that their endpoint was not recorded; nothing is guessed or backfilled.

Raw exceptions, stacks, addresses, emails, tokens and credentials are not copied into this history. The page offers no delete, edit or raw-log endpoint. Existing job/business data is unaffected, and log history has no automatic deletion policy. Older records without `kind` remain visible as server errors; no record rewrite is required.

Writes use a bounded background queue (500 waiting records, batches of 50); requests never wait for logging. Failed batches and excess records are counted in memory for that server run and disclosed by the page. These counters reset on restart. Unflushed records can be lost on termination; a database outage can prevent persistence. This is operational support history, not a complete audit trail or independent outage monitor. Errors loading the log viewer itself do not recursively create entries. Index creation joins the existing startup index retry routine.

For investigation, copy the event reference and request ID. The timestamp and category help the developer find the matching technical log. Do not use the number of entries alone to judge software quality: retries and integration failures can produce multiple records for one underlying issue.
